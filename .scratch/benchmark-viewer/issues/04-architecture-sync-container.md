# 容器怎么组织？同步和前端怎么做？

## Question

基于 01（API 形态）和 02（许可红线）与用户敲定：

- 形态：静态站（同步时预生成 JSON + 纯前端图表，nginx 提供）还是带小后端；倾向前者，理由和反例都要过一遍。
- 图表库选型（原生 SVG / D3 / ECharts 等），是否离线可用（不依赖外部 CDN）。
- 同步机制：容器内 cron 还是宿主机计划任务；失败时保留上次数据并在页面显示"数据日期"。
- 是否保留历史快照；数据放卷（volume）还是烘进镜像。
- 运行环境：Windows 上 Docker Desktop，端口与启动方式。

产出：架构决策 + 容器目录结构 + 同步失败的回退策略。

## Answer

用户于 2026-09-29 确认：

**形态**：单个 **OpenResty** 容器（镜像 `openresty/openresty:alpine`），纯静态前端，不写同步脚本、不用 cron、不用后端。用户提出"只做前端、只要缓存好数据"，最终裁定：**缓存放在容器里的 OpenResty（`proxy_cache`），不是浏览器直连官方接口**。

理由：上游请求次数只取决于 TTL，与访问人数无关（合规）；同源代理避开官方 POST 接口和 BenchLM 文件的 CORS 未验证风险；上游故障时对所有访问者都返回旧数据。

**代理接口（只读，地址和请求体写死，不做开放代理）**
- `GET /api/leaderboard` → 固定 POST 到官方接口（请求体见工单 06 的答案）。
- `GET /api/benchlm/<file>.json` → BenchLM `/data/<file>.json`，只放行前端需要的文件（价格、模型）。

**缓存与超时**

| 项目 | 取值 |
|---|---|
| 官方榜单缓存 | 6 小时 |
| BenchLM 数据缓存 | 24 小时 |
| 上游故障 | 继续返回旧数据，最长 7 天；页面顶部显示数据日期，过旧时提示 |
| 连接超时 / 读取超时 | 5 秒 / 30 秒 |
| 缓存过期时并发请求 | 加锁，只放一个请求出去 |

**前端**：D3（仅比例尺与线段模块）加原生 JS，D3 文件放进仓库，不依赖 CDN，无构建步骤。

**访问范围**：仅局域网，不上公网。默认端口 8088（本机 7860 已被容器 `modeltrace` 占用），可用 `docker run -p` 改。

**数据联接**：官方行到 BenchLM slug 的映射表放在仓库的一个 JSON 文件里，由前端读取；映射不上的新模型仍然显示、不带价格，页面提示"有 N 个新模型缺映射"。不保留历史快照，只保留缓存里那一份。

**合规约束（来自工单 02、06）**：请求带可识别的 User-Agent；只代理白名单文件；页脚署名 "Data from BenchLM.ai" 加链接和 CC BY-NC 4.0 许可，并署名官方榜单来源；数据运行时缓存，不烘进镜像。

**实现时需要验证的技术点**：固定请求体转发官方 POST 并缓存、`proxy_ssl_server_name` 与容器内 DNS `resolver`、BenchLM 大文件的体积与压缩、`proxy_cache_use_stale` 在上游故障和超时下的实际行为、容器的重启策略与健康检查。


## 修订（2026-09-29，spec 评审后）

以 `spec.md` 为准的三处修订：
1. "旧数据最长 7 天"作废：nginx 缓存淘汰按最后访问时间计，页面常被访问则永不过期；改为不设硬上限，靠 48 小时警告提示。
2. 回退条件追加 403、429；只缓存 200；缓存目录挂命名卷。
3. 上游地址、缓存时长、冷却时间改为环境变量可配（默认生产值），以支持模拟上游测试。
